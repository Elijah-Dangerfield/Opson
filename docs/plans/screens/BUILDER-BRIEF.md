The instructions every screen-building agent works from. A screen is planned in its own file in this folder, built to that plan, and reviewed against `docs/practices/review-checklist.md`.

## How to work (this is the agentic process the owner asked for)
1. **Re-plan against reality.** Re-read your plan(s) and reconcile them with the real APIs. Edit the plan file(s) in place where reality differs (state fields, actions, repository calls), and commit that first as a `docs:` commit. The plan is the contract the reviewer checks your code against.
2. **Build to the plan.** One `SEAViewModel` per screen/sheet; state is one immutable data class built by a pure `XStateBuilder` (shared.md); every nutrition number in state is a `Display`/`MacroPart`/`RingValue` from the policy (detekt `HardcodedDisplay` fails the build otherwise); actions are named for user intent or arrivals (never UpdateX/SetX/UpdateState); one-off effects are events; composables are stateless `XScreen(state, onAction)` / `XSheetContent(state, onAction)` and never navigate; entry points route via Router.
3. **Copy**: every string in `libraries/resources/src/commonMain/composeResources/values/strings_<feature>.xml` (a NEW file per feature, not the shared strings.xml, to avoid merge conflicts), prefixed `<feature>_`, verbatim from the prototype where it exists. Voice rules in the checklist. No em dashes in copy.
4. **Previews** for every screen and sheet (one theme per screen preview, a separate dark preview; never `PreviewLightDark` on a whole screen, because every preview is also a 390 dp design-sync screenshot): empty, populated, and Blind (plus Nutrient focus where it differs), light and dark. `org.jetbrains.compose.ui.tooling.preview.Preview` only.
5. **Tests**: ViewModel test per action (hand-rolled fakes), StateBuilder tests for every visibility branch your plan's surface table lists, and the fixtures the leak test needs per `blind-leak-test.md` (expose them so the leak-test agent can import them; put them in commonMain behind an obviously named `…Fixtures` object if the contract says so).
6. **Telemetry**: app events per `docs/practices/app-events.md` where the plan names them (never amounts, answers or free text).
7. **Verify**: compile Android and iOS for your modules and `:apps:compose:compileDebugKotlinAndroid :apps:compose:compileKotlinIosSimulatorArm64`, run your modules' tests, run `./gradlew detekt`. Never run a full `./gradlew build` (other agents share the machine). If an Android emulator is running (`adb devices`), you may install `:apps:compose:assembleDebug` and screenshot your screen (`adb exec-out screencap -p`), but do NOT tap "Continue as guest" or anything that creates accounts on the hosted Supabase; if you can't reach your screen without that, skip the emulator.
8. **Self-review** your diff against every line of `docs/practices/review-checklist.md` before reporting, and fix what fails.

## Rules
- Hidden for 0.1 (shared.md "0.1 scope gates"): barcode, photo, voice, fasting, reminders, watch/health, widgets. Hidden means not rendered, not "Coming soon" (except where the handoff itself says "Coming later").
- Conventional Commits (`feat:`/`test:`/`docs:`), each ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- If you need a shared component or domain helper that does not exist, add it to the right library (with a preview/test), not to your feature, and say so in the report.

## Report back (under 500 words)
Branch, commits, what was built (screens, sheets, routes), plan changes, test counts/results, compile/detekt results, any library additions other screens should reuse, any checklist item you could not satisfy and why, and screenshots findings if you took any.
