# Asking for a store rating

Opson asks for a rating with the store's own sheet (StoreKit's `AppStore.requestReview(in:)` on
iOS, Play's in-app review on Android), right after a moment when someone is likely glad they have
the app. The approach is Cards': pick happy moments, ask rarely, never build a dialog of our own.
On top of that, each install asks at one moment only, so the moments can be compared.

Behind `release.reviewAsk` (off by default, on in dev).

## The moments

| Variant | When | Event that calls it up |
|---|---|---|
| `celebration` | "I can do this" on a milestone celebration | `CelebrationCheered` |
| `day_felt_good` | Today wrapped up with "Good" picked for how it felt | `DayClosed`, then the day is read |
| `showing_up` | The first log, wrap-up or check-in of the day, from someone who showed up on 10 of the last 14 days | `ShowedUp` (`MomentWatcher`) |
| `food_approved` | A food they sent from a pack was approved | `FoodApproved` (`MomentWatcher`) |

Nothing here reads an amount, a target or a deficit. A day that "went to plan" is the person's own
"Good", not a number that came in under a goal.

## When it never asks

The `review` prompt goes through the prompt processor ([prompts.md](prompts.md)), so it gets every
global rule: signed in, onboarded, one prompt a session, and **never to someone who said numbers
have been hard**. It only follows moments, never Today opening. The celebration's "I can do this"
is the one moment allowed to follow another prompt in the same session, because it is the
person's own answer to it.

`RealReviewPromptCoordinator` (`:libraries:review:impl`) adds the rules the stores care about. They
are per phone, like the stores' own limits:

- not in the first 7 days after this build first ran;
- 122 days between asks, so at most three a year, inside Apple's three in 365 days;
- not offline;
- not within 30 minutes of trouble: a line logged at error, a call that never reached the server,
  a failed photo estimate, a barcode that found nothing, sign-in failing, or going offline
  (`RecentTrouble`).

An ask is written down before the sheet is requested. If there was no window to show it in, the
ask is given back.

## The experiment

Each install is given one variant at its first happy moment of any kind, at random by the
weights in remote config, and keeps it:

| Key | Default | Meaning |
|---|---|---|
| `release.reviewAsk` | false | Off asks nobody |
| `review.experiment` | `moments-1` | Rename it to give every install a new variant from the current weights |
| `review.weightCelebration` | 1 | Relative share of installs |
| `review.weightDayFeltGood` | 1 | |
| `review.weightShowingUp` | 1 | |
| `review.weightFoodApproved` | 0 | Off: only people who send foods ever reach it, so most installs given it would never be asked. Turn it up when there are enough of them |

Changing a weight moves only installs not yet assigned. Setting a weight to 0 gives that
variant's installs another one. Renaming the experiment reshuffles everyone.

## What can be measured, honestly

**Neither store tells the app whether the sheet showed, or whether anyone rated.** Apple's API
returns nothing, may show nothing (it limits each person to three a year and never shows in
TestFlight), and Play's flow completes the same way whether or not it drew anything. So:

- `review.asked` counts asks per variant, with an `outcome` that is a best guess.
  `likely_shown` on iOS means a new window appeared in the scene within 1.5 seconds; on Android it
  means the review flow stayed open for a second or more. `likely_not_shown` is mostly the store's
  own quota. Treat these as proxies, not facts.
- The real outcome is in the stores: App Store Connect › Ratings and Reviews, and Play Console ›
  Ratings and reviews, both by date. They are totals for the app. They cannot be split by
  variant.

## Reading the board against store ratings

The board is **Opson · Review asks** (`ops/grafana/review-asks.json`, generated by
`generate_db_dashboards.py`). It shows asks per day by variant and by outcome, how installs were
split, and which moments were held back and why.

With every variant running at once, the board tells you which moments reach people (asks per
installs given that moment) and which ones the store mostly refuses (`likely_shown` share). It
cannot tell you which moment earns better ratings, because the store's daily ratings are one
number for all of them.

To learn that, run the variants one at a time.

1. Set one weight to 1 and the others to 0, and rename `review.experiment` (say `celebration-1`).
2. Leave it two weeks. Note the asks per day on the board and the new ratings per day, and their
   average, in each store.
3. Do the same for the next variant.
4. Compare ratings per 100 asks, and the average star, across the windows. Account for releases
   and anything else that moved in the same weeks.

Loki keeps 31 days, so write each window's totals down before they age out.

## Testing it

QA menu › Prompts lists `review` with whether this phone could ask right now. **Show next** asks
the store as Today next settles, logged under the experiment `qa` so it stays off the board. In a
debug build iOS always draws the sheet (and submitting does nothing); in TestFlight it never does.
On Android the sheet only shows for a build installed from Play, internal app sharing included.
