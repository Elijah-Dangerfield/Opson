# Grafana dashboards

Opson's Grafana boards, committed as JSON, one file per dashboard, in the `Opson` folder at
https://cards.grafana.net/dashboards/f/opson. Pushed by hand or through the Grafana MCP server.

| File | uid | Answers |
| --- | --- | --- |
| `app-health.json` | `opson-app-health` | Are people launching it, how long do they stay, how slow is the cold start, and how did the last run end? |
| `connectivity.json` | `opson-connectivity` | How often is the app unusable, and when it is, is that us or the user's network? |
| `onboarding-funnel.json` | `opson-onboarding` | Does anyone get through the first-run flow, and where do they drop? |
| `pulse.json` | `opson-pulse` | Is the app healthy, and is anyone using it? Start here: client telemetry flowing, crash-free launches, loggers, installs, sessions, unreachable installs, guard stops. |
| `users.json` | `opson-users` | Who uses Opson: population, new and returning loggers, modes, platforms and builds, and the roster. Each user id links to User detail. |
| `user.json` | `opson-user` | Everything about one person: account and email, every build they ran, Settings choices, logging per day by method, features, sessions, guard, sync health, warnings, and a Sentry link. |
| `logging.json` | `opson-logging` | How do people add food: method, precision, meals per day? |
| `modes.json` | `opson-modes` | Which visibility modes do people choose, and how often does the pause stop someone? |
| `foods.json` | `opson-foods` | Is the food database good enough? Zero-result searches, barcode misses, and whether each food's calories add up to its macros (by source, and the furthest off). |
| `retention.json` | `opson-retention` | Do people keep logging? Weekly cohorts and day 1/7/30. |
| `food-review.json` | `opson-food-review` | Are people's foods getting reviewed? The queue, its age, submissions and decisions per day, the approval rate, every pending item linked into the admin console, and the app's Add this food funnel. |
| `builders.json` | `opson-builders` | Is anyone entering fake data, and who? Submissions, reports and corrections per day by state, the queues, every contributor's volume, approval rate, disagreement with the label reading and pace, impossible values, duplicate photos, top reported foods, device checks and bans. Each account id opens the admin console to moderate it. Alert rules beside it in `alerts/builders.json`. |
| `review-asks.json` | `opson-review-asks` | Which happy moment to ask for a store rating at? Asks per moment and outcome by day, the split of installs, and asks held back and why. Read against the stores' ratings by date (`docs/practices/review-asks.md`). |

The last ten are generated by `generate_db_dashboards.py`: edit the script,
run it, push the files. They read Postgres first and Loki where only the app
knows (sessions, crashes, guard, unreachable calls). Loki keeps 31 days;
anything that has to look further back comes from Postgres.

**One `env` dropdown drives every generated panel.** Its value is the Postgres
datasource (`opson-prod-db` or `opson-db`) and its text is the Loki
`deployment_environment` (`prod` or `dev`), written `${env:text}` in the
queries, so a board can never show prod's database beside dev's events. The
three hand-written Loki boards keep their own `env` (`prod` or `dev`).

**Two schemas.** The product boards read `analytics` (aggregates only). Users
and User detail read `support` (V22): one row per person or per person and day,
with counts, timestamps and Settings choices, never a food, an amount, a weight
or a note. Only User detail selects an email (`DashboardQueryContractTest`
holds that). User detail finds a person's app events in Loki by the install ids
the server records for the account in `user_installs`, from the 0.2 server on;
before that, or for an account the server has not seen since, its Loki panels
say there is nothing to show rather than matching everyone.

## The Postgres datasource

`opson-prod-db` (the default) and `opson-db` (dev) point at their Supabase
session pooler as that project's `grafana_ro` role. That role can read the
`analytics` and `support` schemas and nothing else (`V9__analytics.sql`,
`V22__support_views.sql`). No panel can show one person's food log, and no
future panel can either, because the role cannot see the tables and no view
carries the log.

The datasource needs its user and password set once in the Grafana UI
(Connections → Data sources): user `grafana_ro.<project ref>`, and the
password from `GRAFANA_RO_DB_PASSWORD` in `apps/server/.env` (dev, `opson-db`)
or `apps/server/.env.prod` (prod, `opson-prod-db`). Copy it without
printing it:

```bash
grep '^GRAFANA_RO_DB_PASSWORD=' apps/server/.env | cut -d= -f2- | tr -d '\n' | pbcopy
```

They are built from the events in [`docs/practices/app-events.md`](../../docs/practices/app-events.md),
which is the taxonomy, and read with the query conventions in
[`docs/practices/observability.md`](../../docs/practices/observability.md).

**These are the template's boards, so they cover the template's events.** A generated app will emit
its own and want its own dashboards; keep these, because the `app.*` and `net.*` questions do not
stop mattering, and add files beside them rather than editing these into something else.

## What has to exist first

**Nothing here has ever rendered real data.** What has been checked is that every query names an
event and an attribute the code actually emits (see below). What has **not** been checked is
anything about rendering — panel types, thresholds, units, query cost at real volume. Nobody has
looked at one of these with data on it. Expect to adjust.

1. **The OTLP credentials exist.** `GRAFANA_OTLP_ENDPOINT` / `GRAFANA_OTLP_TOKEN` reach
   `loadTelemetryMetadata` in build-logic, via GitHub secrets in CI or `grafana.*` keys in
   `local.properties` for a local build. Blank values leave the pipe dormant and every panel here
   stays empty with no error anywhere.
2. **A build has actually run with them.** `app.launched` is the first event through the freshly
   planted tree and doubles as the pipeline smoke test. If
   `{service_name="opson-client"} | event_name="app.launched"` returns nothing in Explore,
   stop here; the dashboards will not tell you why.
3. **The Loki datasource uid matches.** Every panel targets `grafanacloud-logs`, the uid Grafana
   Cloud provisions its Loki datasource under. If your stack differs, rewrite it in one pass:

   ```bash
   printf "Loki datasource uid: "; read -r DSUID
   [ -n "$DSUID" ] && sed -i '' "s/grafanacloud-logs/$DSUID/g" ops/grafana/*.json && unset DSUID
   ```

   Confirm the uid first from **Connections → Data sources → (your Loki) → the URL**, or with
   `/api/datasources` on the stack.

## Importing

Per dashboard, in the Grafana UI: **Dashboards → New → Import → Upload JSON file**. The uid is in
the file, so re-importing updates the existing dashboard rather than making a second copy. No folder
is pinned in the JSON; pick one at import time.

Or with the Grafana MCP server's `update_dashboard` (full JSON, folder `opson`,
overwrite on), which is how the generated boards were pushed on 2026-10-27. Or
over the API, all of them at once:

```bash
printf "Grafana URL (e.g. https://myorg.grafana.net): "; read -r URL
stty -echo; printf "Grafana API token (Editor or Admin): "; read -r TOKEN; stty echo; printf "\n"
if [ -z "$URL" ] || [ -z "$TOKEN" ]; then
  echo "both values are required — nothing sent" >&2
else
  for f in ops/grafana/*.json; do
    jq -n --slurpfile d "$f" '{dashboard: $d[0], overwrite: true, folderUid: ""}' |
      curl -sS -X POST "$URL/api/dashboards/db" \
        -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" --data @- |
      jq -r '"\(.status // "ok")\t\(.uid // .message)"'
  done
fi
unset TOKEN URL
```

### Alert rules

`alerts/builders.json` is generated with the boards: Grafana-managed rules on
`opson-prod-db`, in Grafana's provisioning format, for one contributor sending
more than 15 foods an hour, five flagged submissions in a day, the approval
rate under half over a week, a photo reused across accounts, a spike of
impossible values, a review queue older than 72 hours, and device checks
failing. They land in the `Opson` folder, group `opson-builders`, with no
contact point: route `app=opson, board=builders` to one in Alerting ›
Notification policies. To push them, which overwrites rules with the same uid:

```bash
printf "Grafana URL (e.g. https://myorg.grafana.net): "; read -r URL
stty -echo; printf "Grafana API token (Editor or Admin): "; read -r TOKEN; stty echo; printf "\n"
printf "Folder uid for the rules [opson]: "; read -r FOLDER; FOLDER="${FOLDER:-opson}"
if [ -z "$URL" ] || [ -z "$TOKEN" ]; then
  echo "both values are required, nothing sent" >&2
else
  jq -c '.groups[0].rules[]' ops/grafana/alerts/builders.json | while read -r r; do
    uid=$(jq -r .uid <<<"$r")
    body=$(jq --arg f "$FOLDER" '. + {folderUID: $f, ruleGroup: "opson-builders", orgID: 1}' <<<"$r")
    code=$(curl -sS -o /dev/null -w '%{http_code}' -X PUT "$URL/api/v1/provisioning/alert-rules/$uid" \
      -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -H "X-Disable-Provenance: true" --data "$body")
    [ "$code" = 404 ] && code=$(curl -sS -o /dev/null -w '%{http_code}' -X POST "$URL/api/v1/provisioning/alert-rules" \
      -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -H "X-Disable-Provenance: true" --data "$body")
    printf "%s\t%s\n" "$code" "$uid"
  done
fi
unset TOKEN URL FOLDER
```

The Grafana MCP server's `alerting_manage_rules` (operation `create`) takes
the same fields one rule at a time. Like the boards, `opson-prod-db` needs its
Grafana password set first (above) or every rule errors.

Import is the whole deployment story. Nothing provisions these automatically and nothing syncs edits
back, so **a change made in the Grafana UI is lost on the next import.** Edit the JSON. Terraform or
Grafana's git-sync would fix that and both are a larger commitment than three files deserve before
anyone has looked at one with real data on it.

## Reading them

**One stack, many apps.** Every project generated from this template exports to the same Grafana
Cloud stack, told apart only by `service_name`. A query without that matcher spans every app you have
ever shipped from here, and a result that looks broad probably is.

**Two stream labels, everything else is structured metadata.** `service_name` and
`deployment_environment` are the only labels; `event_name`, `session_id`, `install_id` and every
event attribute are filtered with pipes. Line filters (`|=`) would work and are wrong — they scan the
body instead of the metadata.

**The `$env` dropdown is `prod` / `dev`**, mapping to `deployment.environment` on the export, which
is `dev` for a debug build and `prod` for a release one. A board reading `prod` while you test a debug
build shows nothing.

**Delivery is at-least-once.** A record can rarely ship twice, so raw counts are approximate. Panels
counting *installs* or *sessions* are immune by construction: a duplicate lands in the same series and
collapses. Ratios are two equally affected counts, so they barely move.

**Sampling is per session.** `telemetry.appEventsSampleRate` hashes the session id, so a sampled-out
session contributes nothing at all rather than losing the middle of a funnel.

## How they are kept honest

`DashboardQueryContractTest` (in `:apps:integration`, under the ordinary `./gradlew testDebugUnitTest`
sweep) parses every query in this directory and every `logEvent(...)` call in the source tree, and
fails if a dashboard references an event or an attribute nothing emits.

This is the check a rename would otherwise pass. A panel filtering on `strikes_used` against an app
emitting `strikes` is not an error anywhere: Loki accepts the query, the panel renders, and it renders
**empty** — which is exactly what a healthy panel looks like before launch. The person who finds it is
whoever eventually asks the dashboard a question and believes the blank answer.

Two consequences for anyone editing these files:

- **The LogQL reader is strict on purpose.** It understands the stream selector, label filters and
  `unwrap`, and throws on anything else. Reaching for `| json`, `| logfmt`, `| line_format` or a `|=`
  line filter fails the test rather than slipping through with nothing extracted. If a panel genuinely
  needs one, teach the reader first. That cost is the feature.
- **Ratios go through `__expr__` math** — two Loki targets and a math node — rather than one
  expression naming two events. A single expression would be allowed, but then every attribute in it
  would have to exist on *both* events.
